2. Stage Details

STAGE 01

Scrape — pull raw race pages from FirstCycling

Fetch race results, startlists, and bib numbers from firstcycling.com at a controlled rate and preserve them as typed Python objects on disk. This is the only stage that reaches the public internet; everything downstream works from the pickles.

Inputs

Race URLs per tour/year (wt / pro / d1, rolling 45-day lookback) Backend: cloudscraper Rate limit: 3-8 s + jitter

Key Transformations

  • Race.populate_race() walks the race page, pulls per-rider rows: place, time_gap, rider_id, rider_name, team.
  • scrape_and_add_bib_numbers_to_race() merges startlist bib numbers onto the Race object.
  • Stage races recurse: a Race holds a list of Stage children with their own results.

Outputs

scraped_data/<year>/<tour>/<race>.pkl Race { name, category, date, results: [{place, gap, rider_id, rider_name, team, bib}...], stages: [Stage, ...] # opt. }
Bring your own data: the public copy ships the scrapers' parsing code, not a way past any site's bot protection. Scraping is the most failure-prone step; the pipeline supports --skip-scrape and nothing downstream needs live network.

STAGE 02

Migrate to SQLite — normalize pickles into relational tables

Collapse the nested Race → Stage → results object graph into a SQLite database with stable integer IDs, then backfill the ordinal place_bucket label and bib-number columns. After this stage, the source-of-truth for everything downstream is the DB, not the pickles.

Inputs

Pickled Race/Stage objects SQLite DB: webscrape_tools/database/ database/cycling_races.db

Pipeline Steps (1–5)

  • scrape-lists — fetch race lists for the rolling window.
  • scrape-data — download individual race pages (incremental: dedupes by fc_race_id+year+category; deletes incomplete races before re-ingest).
  • migrate — insert new races into competitions, rider_results, and related tables; derives stage-race dates at migration time and guards against duplicate ingestion (a 2024 dedupe incident is now structurally prevented).
  • place-bucket — backfill nullable place_bucket via 7 bulk UPDATEs.
  • bib — run migrate_bib_number_columns() to populate team/personal bib splits.

Outputs

SQLite tables (key): competitions rider_results (+ place_bucket, bibs) + startlist tables place_bucket rule: 1 → 0 Winner 2–3 → 1 Podium 4–5 → 2 Top 5 6–15 → 3 Top 15 16–30 → 4 Top 30 31–50 → 5 Top 50 51+ → 6 Finisher DNF/DNS → 7
Bucket 7 (DNF/DNS/OTL) is filtered out of the bucket and time-gap training sets because a DNF's "place" is noise. The multiclass probability heads keep it as their 8th class, and since 2026-06 a dedicated DNF head learns P(finish) properly from 1.26M recovered status rows (DNF vs DNS vs OOT vs DSQ distinguished).

STAGE 03

Precompute Features — rider snapshots, race state, Elo ratings

Every rider's state is precomputed as of every competition they entered and stored in rider_competition_snapshots (1M+ rows, history from 2010). Per-race field aggregates live in competition_field_features. Two newer artifacts join them: within-stage-race state rows (rider_race_state) and chronological contested-Elo snapshots.

Inputs

rider_results (all history) competitions race profile metadata race_feature_gradients

Pipeline Steps (6–11)

  • experience — per-rider career/yearly counts, average buckets by type/category, profile averages, recent form, team-quality stats.
  • percentiles — the 19 per-percentile race-shape tables (see Race Features).
  • gradients — parallel slope/shape extraction over the 19 tables → race profile scores.
  • features — batched, resumable writer for rider_competition_snapshots (now incl. the 15 v2_*/v3_* trajectory/EMA form columns) + competition_field_features.
  • race-state — reconstructs mid-race GC standings per completed stage and writes the 23 within-race state features to rider_race_state (validated vs stored final GCs; suspect races get no rows). live
  • elo-snapshots — replays all result sheets chronologically through the contested-comparison Elo engine and saves as-of-then rating snapshots (~575K rows). live

Outputs

rider_competition_snapshots (rider × competition → 57 cols frozen at race start; incl. v2/v3 form) competition_field_features (field stats per race) rider_race_state (23 state cols, stage ≥ 2 of multi-stage races) contested_rating_snapshots .parquet (Elo as-of-then)
Snapshots are frozen at the moment of the race — no look-ahead leakage. The v2_*/v3_* trajectory columns are NULL by design when a rider lacks qualifying history: LightGBM consumes NaN natively, and their names deliberately dodge the pattern-based imputation ('avg_bucket', '_count') in feature_engineering. Do not add defaults for them.

STAGE 04

Assemble Training Data — join snapshots + field + state + targets

Pull the precomputed snapshots out of SQLite, join field features, race-state rows (LEFT JOIN — missing state becomes NULL + a race_state_missing flag), and actual results; run derived feature engineering; split chronologically for early stopping. Side-pipelines produce leak-free out-of-fold (OOF) predictions used as inputs by downstream heads.

Load + Filter

CyclingDataPipeline(DataConfig( start_date='2016-01-01', min_races_career=10, competition_types= [stage, one_day, gc], race_categories=[wt,pro,d1], include_race_state=True, )) # joins rider_competition_snapshots ⨝ competition_field_features ⟕ rider_race_state ⨝ rider_results (place_bucket, time_gap) 668,433 samples · 5,905 comps 2016-01-18 → 2026-08-09

Derived feature engineering (FeatureEngineer)

  • All the classic interaction features: profile_weighted_expected, rider_vs_field_*, relevant_type/category_avg_bucket, team-role flags, form flags, gc_specialist_score, gap features (see Metrics Reference §7).
  • Type-aware imputation (age by tour level; *_avg_bucket → 5.0; *_count → 0) — trajectory v2_*/v3_* and stack columns are exempt and stay NaN.
  • Arm-C stack frame live: bucket + contender heads additionally receive 17 columns — 2 meta-OOF (oof_time_gap_pred, oof_lambdarank_win_p), 11 one-day contest-signature features (stage/GC rows NaN by scope), 4 contested-Elo features. Time-gap, weighted, calibrated, and LambdaRank heads stay on the plain frame.

Splits + OOF

Split by competition date: train = < 95th pct date early_stop = ≥ 95th pct date (cutoff 2026-03-25 last run) OOF side-runs, 5 temporal folds: classifier_expected_bucket (bucket → contender input) oof_time_gap_pred (time-gap → stack input) oof_lambdarank_win_p (LambdaRank → stack input) leak-free: each fold predicted by a model trained without it
The 95/5 split is chronological, not random. All 100% of data eventually trains the final model; the early-stop tail only sets the iteration count and temperatures. True evaluation lives in the experiment framework: 5-fold full-year CV at the production start date, gated since 2026-06-11 on market probability quality (MarketProbabilityEvaluator) rather than winner capture.

STAGE 05

Train Ten LightGBM Heads

Four pipeline steps train the full model suite: train (the five-model core, plus the OOF side-runs and the day-menu retrieval variant), train-lambdarank (full-field probability head), train-gc-outlook (state-aware mid-race GC head, 2 models), and train-dnf (finish-risk head). All artifacts land in models/production/ via ModelRegistry, with the previous bundle archived.

Shared boosting config

n_estimators 2000 early_stopping_rounds 300 num_leaves 63 learning_rate 0.05 feature_fraction 0.8 bagging_fraction 0.8 bagging_freq 5 min_child_samples 50 seed 42 (contender: lr=0.01; dnf: early_stop=100)

Training sequence (step train)

  • Time gap — regression on log1p(time_gap), finishers only, 3600 s cap. Doubles as the base model for the oof_time_gap_pred stack feature.
  • LambdaRank base + OOF — produces leak-free oof_lambdarank_win_p for the stack frame.
  • Bucket — regression on place_bucket (181 features: 164 incl. state + 17 stack cols). Ranking signal + OOF feed for the contender filter.
  • Probability (weighted) — 8-class softmax, balanced weights, temperature-calibrated (T≈0.76).
  • Probability (calibrated) — 8-class softmax, no weights (T≈0.99).
  • Probability (contender) — 5-class softmax on the top-15 per race by OOF bucket; lr 0.01; consumes classifier_expected_bucket + the 17 stack cols. T≈1.06.
  • Day-menu variant live — after registry.save(): rebuild the day-type signature table DB-fresh, label days against frozen menu v1, compute per-rider kernel cumulants (~642K rides → day_menu_kernels.parquet), train bucket_daymenu (195 = 181 + 14 dtm_* features). Retrieval-only at serve; non-fatal if it fails (production suite is already saved).

Separate steps

  • train-lambdarank — objective='lambdarank', label gains 2rel−1 = [0,1,3,7,15,31,63], ndcg@[1,3,5,10], grouped by competition; per-race softmax with fitted temperature (T≈0.70). 141 features (stateless by design — state variants tested and rejected).
  • train-gc-outlook — bucket + contender pair retrained on 356K mid-race checkpoint rows, state features only.
  • train-dnf — binary P(DNF) head, ~100 features, AUC ≈ 0.889, calibration ratio ≈ 1.01. live

Saved artifacts

Step order matters twice over: the contender model needs the bucket model's OOF predictions, and the bucket/contender pair need the time-gap and LambdaRank base models' OOF outputs plus the Elo snapshot artifact. The pipeline encodes these dependencies; don't run --only train against a stale snapshot/state table after schema changes.

STAGE 06

Inference — predict a race

Given a startlist (scraped for future races, or a competition ID for past ones), pull each starter's most recent snapshot, re-age the 21 form features to the prediction date, rebuild field features from the actual startlist, attach the race fingerprint from reference editions, run every head, and merge into one ranked DataFrame.

Inputs

FirstCycling URL + startlist (future race) OR competition_id (known race) Loaded: latest rider snapshots field features (startlist) reference-edition race profile rider_race_state (if mid-race) contested-Elo snapshots signature context (one-day) day-menu kernels (keyed stages)

Flow

  • assemble_prediction_df() merges snapshots + startlist + field + reference profile; live form re-aging (live_form.py, default on) recomputes all 21 form features as of today — without it, days_since_last_race is stale for 100% of riders (mean 7 days vs true 43).
  • Stack columns default to NaN (LightGBM's trained "unavailable" branch); attach_stack_features() overwrites them with real values — base-model predictions, Elo as-of-today, one-day signatures from references + startlist. live
  • FeatureEngineer.transform() reuses the fitted column set — identical schema vs training, per head.
  • Bucket score (+ time gap) → ranking; multiclass cascade → cumulative probabilities → odds; LambdaRank → calibrated win/podium; GC outlook if state rows exist.
  • Pricing layer: win corrector (logit shift) → 0.2/0.8 cascade–LambdaRank blend → finisher-conditioned market probabilities × the DNF head's P(finish); each step book-preserving. live
  • Day-type keyed serving (campaign toolchain, predict_stage_scenarios.py — not yet a web-app input): a day_key attaches the keyed item's composition + rider kernels and re-ranks the board with bucket_daymenu; promoted riders get contender pricing via extra_contender_ids; prices always come from the production heads. live

Output DataFrame

rider_id, rider_name predicted_rank (1 = winner) expected_bucket (continuous) ranking_score predicted_time_gap (sec) prob_win … prob_dnf (8 cumul.) odds_* (decimal, cap 999) is_contender lambdarank_win_p, _podium_p gc_outlook_* (when mid-race)

STAGE 07

Web App — Streamlit frontend

Paste a FirstCycling URL; the app loads .env (so future-race startlist scrapes use the browser backend), matches riders to the DB, picks reference editions for the race fingerprint, predicts, displays, and logs. See Reading the Predictions for the user-facing guide.

User flow

  • Step 1 — race URL (+ optional stage hint, force-refresh).
  • Step 2 — reference editions: auto-defaults from the same race's history; searchable; shows each edition's profile scores, finishing-distribution metrics, and field composition.
  • Step 3 — predictions: one tab per reference + an averaged-references tab.
  • Step 4 — post-race: scrape actuals, predicted-vs-actual tables, accuracy metrics (Kendall τ, top-3/5 precision, bucket MAE, gap MAE).

What's displayed

  • Ranked table: rank, rider, team, expected bucket, contender flag, time gap.
  • Both probability heads side-by-side: multiclass Win/Podium/Top 5/Top 15 % and LambdaRank Win/Podium %, with Δ Win pp and a yellow highlight when |Δ| ≥ 2pp.
  • Odds expander: decimal / American / fractional for Win → Top 30.
  • GC Outlook section when predicting the GC of an in-progress stage race: outlook rank, current GC rank, formatted gap, Win/Podium/Top 5/Top 15 %.

Prediction log

prediction_log (SQLite) predicted_at, fc_race_id, year, stage_number, competition_id, rider_id, reference_comp_ids (JSON), model_version, multiclass_{win,podium, top5,top15}_p, lambdarank_{win,podium}_p, lambdarank_temperature, state_through_stage, gc_outlook_{win,podium, top5,top15}_p → long-term book comparison

Day-menu retrieval — dtm_* live

dtm_sig_sprintdtm_sig_mountaindtm_sig_hilly dtm_sig_rollingdtm_sig_breakawaydtm_sig_time_trial dtm_sig_wg_prop dtm_rider_sig_sharedtm_rider_sig_vs_field dtm_rider_contest_fit dtm_k_exposdtm_k_attend dtm_k_top3dtm_k_perf_place

The 14 day-type columns seen ONLY by bucket_daymenu (the keyed retrieval ranker) — never by any pricing head (gate verdict: feature attachment in pricing heads costs +0.011 honest log loss, 0/5 folds). Fills = the keyed item's canonical composition; kernels = per-rider similarity-weighted history on days like this (exposure / attendance / top-3 rate / mean finish; γ=8 composition kernel, 730-day half-life, strictly as-of race morning). Unkeyed rows all-NaN.

Imputation Strategy

Age: tour-level medians (wt=28, pro=26, d1=24, default 27).
Bucket averages → 5.0; counts → 0; field stats → fixed defaults.
Race state missing → neutral defaults + race_state_missing=1.
Never imputed (NaN by design): v2_*/v3_* trajectory, sig_*, contested_rating*, oof_* — LightGBM routes NaN down its trained "unavailable" branch.

Data volumes & known skew
  • 668,433 training samples, 5,905 competitions, 2016-01-18 → 2026-08-09 (DB current to 2026-08-09, incl. the full Tour de France 2026 and the healed 2025 late-season block).
  • Snapshots table covers 2010 → present (1M+ rows) so 2016-era training rows still see real career history.
  • Heavily imbalanced: bucket 6 ≈ 58%, bucket 0 ≈ 0.9%. Sample weights / class filters cope.
  • Training filters: start_date ≥ 2016-01-01 (moved from 2018 on 2026-04-18 after a scaling sweep), races_career ≥ 10.
  • DNF labels (separate head): 1.26M status rows recovered from pickles, 132,892 DNFs ≈ 10.6%.
Pipeline step names (CLI)

scrape-lists → scrape-data → migrate → place-bucket → bib → experience → percentiles → gradients → features → race-state → elo-snapshots → train → train-lambdarank → train-gc-outlook → train-dnf

Run one step: uv run python -m cycling_project.update_pipeline --only train. Skip scraping: --skip-scrape. Dry-run plan: --dry-run. Fatal-on-failure: migrate, percentiles, gradients, features. Non-fatal: scraping, race-state, elo-snapshots, all training steps.

Experiment framework & quality gate (out of band)

Production training has no true val set — evaluation goes through prediction_tools/experiment_runner.py with 5-fold full-year CV at the production start date. Since 2026-06-11 the primary gate is MarketProbabilityEvaluator: per-market log loss / Brier / calibration ratio over the binary win, podium, top-5 and top-15 markets for every priced rider, headline = market_avg_log_loss.
