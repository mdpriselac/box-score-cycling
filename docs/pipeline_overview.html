2. Stage Details

STAGE 01

Scrape — pull raw race pages from FirstCycling

Fetch race results, startlists, and bib numbers from firstcycling.com at a controlled rate and preserve them as typed Python objects on disk. This is the only stage that reaches the public internet; everything downstream works from the pickles.

Inputs

Race URLs per tour/year (wt / pro / d1, rolling 45-day lookback) Tour levels: wt, pro, d1 Scraper: cloudscraper session Rate limit: 3-8 s between requests

Key Transformations

  • WebClient.get() — cloudscraper-based GET with min 3 s spacing + jitter, handles Cloudflare challenges.
  • Race.populate_race() walks the race page, pulls per-rider rows: place, time_gap, rider_id, rider_name, team.
  • scrape_and_add_bib_numbers_to_race() merges startlist bib numbers onto the Race object so team_bib / personal_bib are available downstream.
  • Stage races recurse: a Race holds a list of Stage children with their own results.

Outputs

scraped_data/<year>/<tour>/<race>.pkl Race { name, category, date, results: [{place, gap, rider_id, rider_name, team, bib}...], stages: [Stage, ...] # opt. }
Scraping is the slowest and most failure-prone step. The pipeline supports --skip-scrape and resumes from pickle state on crash — nothing downstream needs live network.

STAGE 02

Migrate to SQLite — normalize pickles into relational tables

Collapse the nested Race → Stage → results object graph into a SQLite database with stable integer IDs, then backfill the ordinal place_bucket label and bib-number columns. After this stage, the source-of-truth for everything downstream is the DB, not the pickles.

Inputs

Pickled Race/Stage objects SQLite DB: webscrape_tools/database/ database/cycling_races.db

Pipeline Steps (1–5)

  • scrape-lists — fetch race lists for the rolling window.
  • scrape-data — download individual race pages (incremental: dedupes by fc_race_id+year+category; deletes incomplete races before re-ingest).
  • migrate — insert new races into competitions, rider_results, and related tables.
  • place-bucket — backfill nullable place_bucket via 7 bulk UPDATEs using the bucketing rule (see table below).
  • bib — run migrate_bib_number_columns() to populate team/personal bib splits.

Outputs

SQLite tables (key): competitions rider_results (+ place_bucket, bibs) + startlist tables place_bucket rule: 1 → 0 Winner 2–3 → 1 Podium 4–5 → 2 Top 5 6–15 → 3 Top 15 16–30 → 4 Top 30 31–50 → 5 Top 50 51+ → 6 Finisher DNF/DNS → 7
Bucket 7 (DNF/DNS/OTL) is generated by the place-bucket backfill but is filtered out of the bucket and time-gap training sets downstream because the "place" for a DNF is noise. The probability model still learns P(DNF) as its 8th class.

STAGE 03

Precompute Features — build rider + field snapshots

Every rider's state is precomputed as of every competition they entered (experience, recent form, profile specialization, team quality) and stored in rider_competition_snapshots. Per-race field aggregates (size, bucket distribution, specialist counts, race profile scores) are stored in competition_field_features. This materialization is what makes later training and inference fast.

Inputs

rider_results (all history) competitions race profile metadata

Pipeline Steps (6–9)

  • experience — per-rider career/yearly race counts, average buckets by race type (stage/one-day/gc) and category (wt/pro/d1), profile averages (sprint/mountain/hilly/rolling/breakaway/tt), recent form (avg, best, delta, days-since-last), team-quality stats.
  • percentiles — build lookup tables used by field-level statistics.
  • gradients — parallel elevation/gradient extraction (8 worker threads) → race profile scores.
  • features — batched (100/commit, resumable) writer that materializes rider_competition_snapshots + competition_field_features.

Outputs

rider_competition_snapshots (rider × competition → ~40 rider features frozen at that race's start date) competition_field_features (one row per competition with field stats + race profile scores)
Snapshots are frozen at the moment of the race, so loading training data for a 2020 race gives you the rider's stats as of 2020 — no look-ahead leakage from later races bleeds in. The same snapshot table is read by both training and inference.

STAGE 04

Assemble Training Data — join snapshots + field + targets

Pull the precomputed snapshots out of SQLite, join them to per-race field features and actual results, run derived feature engineering, and split chronologically for early stopping. A separate OOF side-pipeline produces leak-free bucket predictions for the contender model.

Load + Filter

CyclingDataPipeline(DataConfig( start_date='2018-01-01', min_races_career=10, competition_types= [stage, one_day, gc], race_categories=[wt,pro,d1], )) # joins rider_competition_snapshots ⨝ competition_field_features ⨝ rider_results (place_bucket, time_gap)

Derived feature engineering (FeatureEngineer)

  • rider_vs_field_bucket_gap, rider_vs_field_experience_ratio
  • profile_match (rider best profile == race dominant profile)
  • profile_weighted_expected — Σ (rider profile avg × race profile score)
  • relevant_type_avg_bucket, relevant_category_avg_bucket
  • is_team_leader, is_protected_rider, experience_tier
  • field_quality_score, matching_specialists_in_field
  • form_vs_field_gap, is_improving_form, is_fresh, is_rusty, form_confidence
  • type_experience_ratio (√-compressed), gc_specialist_score (Bayesian shrinkage k=10), gc_vs_career_gap, mountain_vs_career_gap
  • is_team_best, team_support_ratio, rider_vs_team_gap
  • Type-aware imputation: age by tour level (wt=28, pro=26, d1=24, default=27), *_avg_bucket → 5.0, *_count → 0
  • Encode: competition_type one-hot, race_category ordinal (wt=0, pro=1, d1=2), best_profile / race_dominant_profile one-hot

Splits + OOF

Split by competition date: train = < 95th pct date early_stop = ≥ 95th pct date (early_stop is NOT a val set — used only for LightGBM early stopping + temp calibration) OOF bucket predictions (contender model only): 5 temporal folds on train → classifier_expected_bucket leak-free, used as feature in contender training
The 95/5 split is chronological, not random — last 5% of competitions by date. Because all 100% of data eventually trains the final model, this avoids wasting signal on a held-out val set while still giving LightGBM a stopping criterion. True model evaluation lives in the experiment framework, not here.

STAGE 05

Train Five LightGBM Models

One call to train_production_model.main() trains five models on the same feature matrix, each with a different objective/filter, and hands the whole bundle (plus metadata) to ModelRegistry. All five share boosting hyperparameters — the differences are objective, class/sample filter, and (for contender) an extra OOF input feature.

Shared config

n_estimators 2000 early_stopping_rounds 300 num_leaves 63 learning_rate 0.05 feature_fraction 0.8 bagging_fraction 0.8 bagging_freq 5 min_child_samples 50 seed 42

Training sequence

  • Bucket — regression objective on place_bucket (0–7 treated as continuous). Sample-weighted for imbalance. Also produces predict_continuous() (used as the ranking signal) and predict_proba().
  • Time Gap — regression on log(time_gap + ε). Trained only on finishers; exclude_winners=True and max_time_gap=3600 s cap. Bucket 7 (DNF) rows dropped.
  • Probability (weighted) — 8-class multiclass softmax over all buckets, with balanced sample weights. Temperature calibrated on the early-stop set.
  • Probability (calibrated) — 8-class softmax, no sample weights, also temperature-calibrated. Produces better-calibrated probabilities at the cost of winner capture.
  • Probability (contender) — 5-class softmax (buckets 4–6 merged), trained only on top-15 riders per race ranked by OOF classifier_expected_bucket. Lower learning rate (0.01), uses the OOF bucket value as an input feature.

Saved artifact

models/production/ bucket_model.txt bucket_feature_engineer.pkl time_gap_model.txt time_gap_feature_engineer.pkl probability_model_weighted.txt probability_model_calibrated.txt probability_model_contender.txt *_feature_engineer.pkl metadata.json (temperatures, iters, sample counts, date range) history/<ts>_... (archived previous model)
The contender model uses OOF predictions from a side-run of the bucket model as an input feature — this is why step order matters. 5 temporal folds train mini bucket models on 4/5 of the data to score the held-out fold, then the top-15 filter is applied to those leak-free scores before reducing the target to 5 classes.

STAGE 06

Inference — predict a race

Given a competition ID, the API pulls each starter's most recent snapshot, rebuilds field features from that startlist, runs the same FeatureEngineer.transform() used at training, invokes all three predictor families, and hands results to the RaceRankingPredictor for final ordering.

Inputs

competition_id (known race) OR FirstCycling URL + startlist (future race — see Stage 7) Loaded from DB: rider_competition_snapshots competition_field_features (or computed on-the-fly)

Flow

  • RacePredictionAPI.load(model_dir) → pulls all 5 predictors + RaceRankingPredictor via ModelRegistry.load_with_ranker().
  • predict_race(competition_id) → loads startlist DF via data_pipeline.load_race_startlist().
  • FeatureEngineer.transform() reuses the fitted column set (guarantees identical schema vs training).
  • Bucket predictor → continuous score used for ranking sort.
  • Probability predictors → 8-class / 5-class softmax → cumulative labels (win, podium, top5, top15, top30, top50, finish, dnf) → decimal / fractional / American odds (capped at MAX_ODDS=999.0).
  • Time-gap predictor → seconds behind winner (finishers only; winners get 0; DNFs get NaN).
  • RaceRankingPredictor combines all signals into one ranked DataFrame.

Output DataFrame

rider_id, rider_name predicted_rank (1 = winner) predicted_bucket (int) expected_bucket (continuous) predicted_time_gap (sec) P(win), P(podium), P(top5), P(top15), ..., P(dnf) decimal_odds / american_odds per cumulative label

STAGE 07

Web App — Streamlit frontend

The interactive surface: paste a FirstCycling URL, the app matches riders to the DB, rebuilds field features on the fly, runs prediction, and displays ranked tables plus odds. Optionally scrapes actual results post-race and compares them to the predicted ranking.

User flow

  • Paste FirstCycling race URL (optionally with a stage hint).
  • parse_firstcycling_url() → race_id / year / stage.
  • scrape_or_load_startlist() → riders at the start line.
  • match_riders_to_db() joins them to internal rider_ids.
  • get_latest_rider_snapshots() pulls most-recent precomputed features.
  • compute_field_features() + get_reference_race_profile() assemble the race context.
  • assemble_prediction_df() → hand to ModelRegistry.load_with_ranker().

What's displayed

  • Ranked rider table (by expected bucket).
  • Cumulative probability columns (win / podium / top5 / top15 / top30 / top50 / finish / dnf).
  • Sportsbook-style odds in decimal, fractional, and American.
  • Expected time gap column for fitted finishers.
  • Field quality stats + race profile breakdown.
  • Optional: actual-vs-predicted evaluation once results are scraped.

Downstream hooks

Model loader: MODEL_DIR = models/production ModelRegistry.load_with_ranker() Odds format: _decimal_to_american(d) Reference race profiles: default / auto-detected / manual stage picker

3. Feature Taxonomy

What the model actually "knows" about each (rider × race) pair, grouped by semantic role. All features come from feature_engineering.py (base groups lines 52–98, derived features lines 162–332).

Rider — History

ageraces_careerraces_this_year stage_avg_bucketstage_count one_day_avg_bucketone_day_count gc_avg_bucketgc_count wt_avg_bucketwt_count pro_avg_bucketpro_count d1_avg_bucketd1_count

Career volume + average bucket by race type (stage / one-day / gc) and by tour category (wt / pro / d1). Frozen at the start date of each race — no lookahead.

Rider — Profile Specialization

sprint_avg_bucketmountain_avg_bucket hilly_avg_bucketrolling_avg_bucket breakaway_avg_buckettime_trial_avg_bucket best_profile

Per-profile average buckets ⇒ the 6-way specialization vector. best_profile is the argmin over the six. Combined with race profile scores via profile_weighted_expected.

Rider — Form

form_recent_avg_bucketform_recent_best_bucket form_recent_countform_delta form_profile_recent_avgdays_since_last_race

Short-window recency signals. Derived features add is_improving_form, is_fresh (<14 days), is_rusty (>45 days), form_confidence (= form_recent_count / 5).

Rider — Team Context

team_bibpersonal_bib team_quality_meanteam_quality_median team_quality_stdteam_quality_min team_quality_maxteam_quality_p25 team_quality_p75team_size team_depth

Derived: is_team_leader (personal_bib==1), is_protected_rider (∈{1,2,3}), is_team_best, team_support_ratio, rider_vs_team_gap.

Field — Aggregates

field_size experience_meanexperience_median experience_stdexperience_min experience_maxexperience_p25 experience_p75 bucket_meanbucket_median bucket_stdbucket_min bucket_maxbucket_p25 bucket_p75

Precomputed once per competition. Derived: field_quality_score = (5 − bucket_mean)/2, plus rider_vs_field_bucket_gap and rider_vs_field_experience_ratio.

Field — Specialist Counts

sprinter_countclimber_count hilly_specialist_countrolling_specialist_count breakaway_specialist_counttime_trialist_count unknown_profile_count

matching_specialists_in_field picks the count that matches the race's dominant profile, so the model sees "how crowded is this specialty at this race?"

Race — Profile + Category

race_sprint_scorerace_mountain_score race_hilly_scorerace_rolling_score race_breakaway_scorerace_time_trial_score race_dominant_profile competition_typerace_category

6 real-valued profile scores computed from gradients + finishing patterns. Encoding: competition_type one-hot; race_category ordinal (wt=0, pro=1, d1=2); race_dominant_profile one-hot.

Derived — Interaction + Specialization

profile_match profile_weighted_expected relevant_type_avg_bucket relevant_category_avg_bucket best_profile_bucket type_experience_ratio gc_specialist_score gc_vs_career_gap mountain_vs_career_gap experience_tier

The most predictive engineered signals. gc_specialist_score Bayesian-shrinks gc_avg toward 5.0 with k=10 (handles small samples). type_experience_ratio √-compresses to undo stage-race inflation. Gap features were validated as +19.3% winner / +25.3% podium capture vs baseline.

Imputation Strategy

Age: tour-level medians (wt=28, pro=26, d1=24, default 27) when missing or ≤ 0.
Bucket averages: fill with 5.0 (mid-field expectation).
Counts (*_count, races_career, races_this_year): fill with 0.
Field stats: fixed defaults (field_size=100, bucket_mean=5.0, bucket_std=1.5…).
Applied in FeatureEngineer.apply_imputation() after derived-feature creation.

Data volumes & known skew
  • ~468K training samples, ~4,307 competitions, 2018 → present.
  • Heavily imbalanced: bucket 6 (Finisher 51st+) ≈ 58%, bucket 0 (Winner) ≈ 0.9%. Sample weights or class filters (contender model) are how the bucket/weighted probability model cope.
  • Bucket 7 is filtered out of bucket & time-gap training sets; the probability models retain it as class 7.
  • Training filters: start_date ≥ 2018-01-01, races_career ≥ 10 (requires meaningful rider history).
Pipeline step names (CLI)

scrape-lists → scrape-data → migrate → place-bucket → bib → experience → percentiles → gradients → features → train

Run one step: uv run python -m cycling_project.update_pipeline --only train. Skip scraping: --skip-scrape. Dry-run plan: --dry-run.

Experiment framework (out of band)

Production training has no true val set — real model evaluation goes through prediction_tools/experiment_runner.py, which runs 3-fold full-year CV (train→2021/test 2023, train→2022/test 2024, train→2023/test 2025) to avoid seasonal bias. Results are saved as JSON under experiments/. See experiment_log.md for the history of accepted / rejected changes.
